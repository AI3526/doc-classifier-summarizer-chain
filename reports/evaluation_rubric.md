# 요약 평가 기준

생성 모델이 만든 문서 요약을 어떻게 채점하고 비교하는지 정리한 문서다. 생성 모델 비교를 실행하기 전에 정했고, 평가 데이터(`generation_eval.jsonl`)의 결과를 본 뒤에는 바꾸지 않는다.

- 채점 체크리스트 버전: `summary_checklist_v1` (`steps/prompts/judge_prompt.py`)
- 점수 공식: `steps/common/quality.py`
- 실행: `steps/step09b_score.py` (`judge` / `sheet` / `aggregate`)

---

## 1. 원칙

1. **원문만 근거로 판단한다.** 같은 뜻의 다른 표현은 인정하고, 미정과 확정을 구분한다(데이터의 `rubric_note`).
2. **사람과 LLM이 같은 체크리스트를 채운다.** 점수는 체크 결과에서 같은 공식으로 계산한다. 그래야 항목별로 사람과 LLM의 판단을 직접 비교할 수 있다.
3. **판단은 예/아니오처럼 작게 나눈다.** 큰 점수를 한 번에 매기는 것보다 채점자 사이의 판단이 잘 일치한다.
4. **채점 기준은 채점에만 쓴다.** `required_points`, `forbidden_claims`, `expected_label`은 생성 프롬프트에 넣지 않는다. `scripts/verify_service.py`가 프롬프트에 섞이지 않았는지 확인한다.

## 2. 채점 기준의 출처

평가 데이터의 문서마다 다음이 제공된다.

| 필드 | 내용 | 기본 데이터 개수 |
|---|---|---|
| `required_points` | 요약에 꼭 들어가야 할 핵심 내용 | 문서당 3개 |
| `forbidden_claims` | 요약이 하면 안 되는 주장(흔한 오해, 지어내기 쉬운 내용) | 문서당 2개 |
| `rubric_note` | "원문의 의미를 기준으로 평가합니다. 같은 뜻의 표현을 인정하고 미정과 확정을 구분합니다." | – |

모범 요약문은 제공되지 않는다.

## 3. 검토했지만 쓰지 않은 방법

| 방법 | 쓰지 않은 이유 |
|---|---|
| ROUGE-1/2/L | 모범 요약문과 단어가 겹치는 정도를 보는 지표인데, 이 데이터에는 모범 요약문이 없다. 출력이 JSON 필드로 나뉘어 문장 비교와 맞지 않고, 한국어는 조사 때문에 형태소 분석 없이는 점수가 크게 흔들린다. |
| 항목별 0~2점 (정책 적합, 핵심 포함, 근거 없는 주장, 명료성) | 기준 자체는 타당하지만 "1점"의 경계가 모호해 채점자마다 판단이 달라지기 쉽다. 같은 네 기준을 아래 체크리스트로 더 잘게 나눠 그대로 이어받았다. |
| 100점 감점식만 사용 | 서비스 관점의 치명도를 반영하는 장점이 있다. 하지만 숫자 하나로는 어떤 실패인지 보이지 않고, 같은 실수가 여러 번 나와도 한 번만 감점된다. 그래서 주 지표가 아닌 **발표용 요약 점수**로 함께 계산하고, 최대 감점 합계를 정확히 100에 맞춰 나쁜 결과끼리도 0점에 몰리지 않게 했다. |

## 4. 체크리스트

응답 하나마다 아래를 채운다. 사람 시트의 칸과 LLM 채점 출력의 필드가 1:1로 같다.

| 항목 | 입력 | 판정 기준 |
|---|---|---|
| 핵심 내용 (`rp1`~) | 포함 / 부분 / 누락 | `required_points`의 각 번호가 요약에 있는지. 일부만 담았으면 부분 |
| 금지 주장 (`fc1`~) | 위반 1 / 0 | `forbidden_claims`의 각 번호를 요약이 주장하면 1 |
| 근거 없는 주장 | 해당 문장 인용, 없으면 빈칸 | 금지 주장 외에 원문에 근거가 없는 내용 |
| 수치·날짜 오류 | 1 / 0 | 수치, 날짜, 시간, 장소, 담당자가 원문과 다름 |
| 외국어 섞임 | 1 / 0 | 외국어 문장이나 불필요한 외국어 단어가 섞임. 원문에 있는 고유명사·약어는 제외 |
| 정책 위반 | 1 / 0 | 제안을 확정 결정으로 씀, 원문에 있는 정보를 "미기재"로 둠, 내용을 엉뚱한 필드에 넣음 |
| 어색한 문장 | 1 / 0 | 문법이 틀리거나 뜻이 잘 통하지 않는 문장 |

**판정 예시** (step07 연습 호출에서 실제로 나온 응답, train 문장)
- 원문: "이번 주 도착한 소형 택배 중 수령인이 확인된 물품만 보관함으로 옮겼다. 대상자에게는 물품 번호를 개별 전달한다. 이름을 확인하지 못한 물품은 안내실에서 따로 보관한다."
- 응답의 `changes`: "이름을 확인하지 못한 물품은 안내실에서 보관하는 방식으로 변경됨"
- 판정: 원문에는 무엇이 "변경"되었다는 내용이 없다 → **근거 없는 주장**(환각). `changes`는 "미기재"가 맞다.

## 5. 지표

### 5.1 체크리스트에서 계산하는 지표

| 지표 | 정의 | 역할 |
|---|---|---|
| **사용 가능률** | 아래 조건을 모두 만족하는 응답의 비율 | **주 지표.** 그대로 사용자에게 보여 줘도 되는 요약이 몇 %인가 |
| 핵심 포함률 | 핵심 내용별 포함 1, 부분 0.5, 누락 0의 평균 | 필요한 내용을 담았나 |
| 환각률 | 금지 주장 위반 또는 근거 없는 주장이 하나라도 있는 응답의 비율 | 가장 위험한 실패 |
| 수치 오류율, 외국어 섞임률, 정책 위반율, 어색한 문장 비율 | 해당 항목이 1인 응답의 비율 | 실패 유형 분석 |
| 100점 감점 점수 | 아래 감점표로 계산 | 발표용 요약 숫자 |

**사용 가능 조건**: 형식 정상 그리고 환각 없음 그리고 수치·날짜 오류 없음 그리고 외국어 섞임 없음 그리고 핵심 포함률 ≥ 0.67(대략 3개 중 2개 이상)

정책 위반과 어색한 문장은 감점에는 반영하지만 사용 가능 조건에서는 뺐다. 읽는 데 불편하지만 잘못된 정보를 주지는 않기 때문이다.

### 5.2 100점 감점표

| 항목 | 감점 |
|---|---|
| 환각 (금지 주장 위반 또는 근거 없는 주장) | −30 |
| 수치·날짜·시간·장소·담당자 오류 | −20 |
| 외국어 섞임 | −15 |
| 정책 위반 | −5 |
| 어색한 문장 | −5 |
| 핵심 내용 누락 | 누락 1개당 −8, 부분 1개당 −4, 합계 최대 −25 |
| **최대 감점 합계** | **−100** |

- 모든 항목이 최대로 감점될 때 정확히 0점이 되도록 맞췄다. 그래서 나쁜 응답끼리도 점수 차이가 남는다.
- 환각 > 수치 오류 > 외국어 > 누락 > 정책·문장 순으로 서비스에 치명적인 정도를 반영했다.
- 각 항목은 있음/없음으로 한 번만 감점한다(같은 실수가 여러 번 나와도 한 번).
- 예: 핵심 내용 3개 중 부분 1개·누락 1개, 어색한 문장 있음 → 100 − (4 + 8) − 5 = 83점

### 5.3 자동 처리

| 상황 | 처리 |
|---|---|
| 응답이 JSON 형식에 맞지 않음(` ```json ` 코드 블록 표시를 걷어 내도 깨짐) | 채점하지 않고 0점, 사용 불가. 형식 실패율로 따로 보고 |
| 코드 블록으로 감쌌지만 안의 JSON은 정상 | 품질 채점은 진행. 형식(엄격) 위반으로 따로 집계 |
| 외국어 섞임 | 원문에 없는 한자·가나·영문 단어가 요약 값에 있으면 자동으로 "있음". 채점자 판정과 둘 중 하나라도 있음이면 있음 |
| 호출 실패(오류, 시간 초과) | 품질 채점 대상이 아니며 오류율로 따로 보고 |

## 6. 채점 절차

### 6.1 생성 비교 단계와 채점 범위

| 단계 | 입력 | 모델 | LLM 채점 | 사람 채점 |
|---|---|---|---|---|
| 1차 비교 | development 15건 × 1회 | 로컬 5개 | 전체 | 하지 않음 |
| 2차 비교 | eval 24건 × 2회 | 1차 상위 로컬 2개 + OpenAI | 전체(144건) | 36건 |

1차 결과로 프롬프트를 고칠 수 있지만, 2차(eval) 결과를 본 뒤에는 프롬프트와 이 문서를 바꾸지 않는다.

1차 결과로 정한 2차 조건(자세한 근거는 [생성 모델 실험 기록](experiment_log_generation.md) 3장):
- 프롬프트 `document_summary_v4`, 구조화 출력 사용
- 로컬 모델 llama3.1-8b, qwen2.5-7b + OpenAI gpt-6-luna

### 6.2 LLM 채점

| 항목 | 값 |
|---|---|
| 채점 모델 | `lesson_settings.JUDGE_TARGET` = openai (gpt-6-luna) |
| temperature | 0 |
| 입력 | 원문, 예측 문서 유형과 정책, 핵심 내용, 금지 주장, 요약(JSON) |
| 재시도 | 출력 형식이 틀리면 1회 다시 시도. 두 번 다 실패하면 채점 오류로 기록하고 집계에서 뺀다 |
| 금지 주장 판정이 빠진 경우 | 위반 없음으로 채운다(위반한 것만 나열하는 경우가 있어서) |
| 핵심 내용 판정이 빠진 경우 | 채점 오류로 처리한다 |

### 6.3 사람 채점

| 항목 | 방법 |
|---|---|
| 대상 | 2차 비교의 반복 1회분 중 형식이 정상인 응답에서 **36건** |
| 표본 추출 | 모델별 12건 × 문서 유형별 4건을 무작위로(seed 2026). 언제 다시 뽑아도 같은 36건 |
| 채점자 | 팀원 4명이 **같은 36건**을 각자 채점(1인당 약 30~40분) |
| 블라인드 | 모델 이름을 가리고 채점자마다 순서를 다르게 섞는다. 모델 대조표(`human_key.json`)는 채점이 끝날 때까지 열지 않는다 |
| 기준 맞추기 | 시작 전에 development 데이터 3~5건을 함께 채점하며 판단 기준을 맞춘다. eval 데이터로 연습하지 않는다 |
| 최종 판정 | 체크 항목별 **다수결**. 2:2 동률은 보수적으로(문제 있음, 부분 포함) 정하고 `ties` 목록에 남겨 함께 논의한다 |

### 6.4 일치도

| 지표 | 대상 | 해석 |
|---|---|---|
| Fleiss' kappa | 사람 4명 사이, 예/아니오 항목별 | 사람끼리 얼마나 같은 판단을 하는지. LLM 일치도를 해석하는 기준선 |
| 일치율, Cohen's kappa, PABAK | LLM 판정 vs 사람 다수결, 항목별과 사용 가능 여부 | LLM 채점을 얼마나 믿을 수 있는지 |
| 피어슨 상관계수 | LLM 감점 점수 vs 사람 감점 점수 | 점수 순위가 비슷한지 |

- kappa는 우연히 일치할 확률을 뺀 값이다. 흔히 0.41~0.60을 보통, 0.61~0.80을 상당한 일치로 본다.
- **kappa의 약점**: 판정이 한쪽으로 몰리면(예: 36건 중 32건이 사용 가능) 실제 일치율이 높아도 kappa가 낮게 나온다. 우연히 일치할 확률이 커져서 그만큼 빼기 때문이다.
- **PABAK** = 2 × 관측 일치율 − 1. 판정 비율이 치우쳐도 덜 흔들린다. 예를 들어 36건 중 34건이 일치하면 PABAK은 0.89다.
- 36건으로 계산한 일치도는 표본이 작아 대략 ±0.2 흔들릴 수 있다. 기준값 근처의 결과는 이 점을 함께 적는다.

## 7. 사람 평가의 역할

사람 평가는 **LLM 채점을 믿을 수 있는지 검증하는 기준**이다. 최종 모델 선택은 아래 순서로 판단한다.

1. 사람 다수결과 LLM의 **사용 가능 여부** 판정으로 일치도를 구한다.
   - 기본 기준은 **Cohen's kappa**다.
   - 사람과 LLM 판정을 합쳐 "사용 가능"이나 "사용 불가" 한쪽이 **85%를 넘으면** kappa 대신 **PABAK**을 기준으로 쓴다.
2. 기준 값이 **0.7 이상**이면 LLM 채점 결과(144건 전체)로 모델을 비교한다. 사람 36건 결과는 함께 보고한다.
3. 0.7 미만이면 LLM 채점은 참고로만 두고, **사람 다수결 결과(36건)를 우선**해 모델을 비교한다. 표본이 작다는 한계를 함께 적는다.
4. 어느 경우든 kappa, PABAK, 관측 일치율을 모두 보고한다. 사람과 LLM이 엇갈린 항목은 사례로 정리해 LLM 채점의 경향(예: 특정 모델에 후함)을 분석한다.

이 판정은 `aggregate`가 `quality_human.json`의 `agreement.llm_trust_decision`에 기록한다(기준 상수: `common/quality.py`의 `AGREEMENT_THRESHOLD`, `SKEW_RATIO`).

## 8. 한계

- **채점 모델의 자기 편향**: OpenAI는 비교 후보이면서 채점 모델이다. 자기 계열의 답변을 후하게 볼 수 있어, 사람 블라인드 채점과의 일치도로 이를 점검한다.
- **사람 채점 표본**: 36건은 모델당 12건이라 모델 사이의 작은 차이는 구분하기 어렵다.
- **체크 단위**: 근거 없는 주장과 각 오류는 있음/없음으로만 보고 개수는 세지 않는다.
- **채점 기준의 범위**: `required_points`와 `forbidden_claims`가 다루지 않는 오류는 "근거 없는 주장"과 기타 항목에 의존한다.
- **사용 가능 기준값**: 핵심 포함률 0.67과 감점 값은 팀이 정한 값이고, 실제 사용자 만족도로 검증한 값은 아니다.

## 9. 파일과 명령

```powershell
uv run python steps/step09b_score.py judge --dir <비교 폴더>      # LLM 채점 (요금 발생)
uv run python steps/step09b_score.py sheet --dir <비교 폴더>      # 사람 채점 시트 생성
uv run python steps/step09b_score.py aggregate --dir <비교 폴더>  # 시트 집계
```

| 파일 (비교 폴더 안) | 내용 |
|---|---|
| `judge.jsonl` | 응답별 LLM 체크리스트, 지표, 채점 비용 |
| `quality_llm.json` | 모델별 LLM 채점 지표 |
| `human/human_sheet_rater1~4.csv` | 사람 채점 시트 |
| `human/human_key.json` | 항목 ↔ 모델 대조표 (채점 후 열기) |
| `human/README.md` | 채점자 안내 |
| `quality_human.json` | 사람 다수결 지표, 일치도 |
