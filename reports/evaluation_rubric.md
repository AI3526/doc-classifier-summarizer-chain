# 요약 평가 기준

생성 모델이 만든 문서 요약을 어떻게 채점하고 비교하는지 정리한 문서다. 평가 데이터(`generation_eval.jsonl`)로 최종 비교를 하기 전에 정했고, 최종 비교 결과를 본 뒤에는 바꾸지 않는다.

- 채점 체크리스트 버전: `summary_checklist_v3` (`steps/prompts/judge_prompt.py`)
- 칸 규칙: `steps/prompts/document_policies.py`의 `FIELD_GUIDES` (생성 프롬프트와 채점 프롬프트가 같은 규칙을 쓴다)
- 점수 공식: `steps/common/quality.py`
- 실행: `steps/step09b_score.py` (`judge` / `sheet` / `aggregate` / `select`)

---

## 1. 원칙

1. **원문만 근거로 판단한다.** 같은 뜻의 다른 표현은 인정하고, 미정과 확정을 구분한다(데이터의 `rubric_note`).
2. **사람과 LLM이 같은 체크리스트를 채운다.** 점수는 체크 결과에서 같은 공식으로 계산한다. 그래야 항목별로 사람과 LLM의 판단을 직접 비교할 수 있다.
3. **판단은 예/아니오처럼 작게 나눈다.** 큰 점수를 한 번에 매기는 것보다 채점자 사이의 판단이 잘 일치한다.
4. **채점 기준은 채점에만 쓴다.** `required_points`, `forbidden_claims`, `expected_label`은 생성 프롬프트에 넣지 않는다. `scripts/verify_service.py`가 프롬프트에 섞이지 않았는지 확인한다.
5. **요약은 자동화에 쓰이는 구조화 데이터로 본다.** 공지의 할 일은 알림, 일정은 캘린더, 회의록의 담당은 작업 지정으로 이어질 수 있다. 그래서 내용뿐 아니라 **각 칸에 맞는 내용이 들어갔는지**도 사용 가능 여부를 가른다.

## 2. 채점 기준의 출처

평가 데이터의 문서마다 다음이 제공된다.

| 필드 | 내용 | 기본 데이터 개수 |
|---|---|---|
| `required_points` | 요약에 꼭 들어가야 할 핵심 내용 | 문서당 3개 |
| `forbidden_claims` | 요약이 하면 안 되는 주장(흔한 오해, 지어내기 쉬운 내용) | 문서당 2개 |
| `rubric_note` | "원문의 의미를 기준으로 평가합니다. 같은 뜻의 표현을 인정하고 미정과 확정을 구분합니다." | – |

모범 요약문은 제공되지 않는다. 칸 규칙은 팀이 정했고, train 문서로 만든 퓨샷 예시(`steps/prompts/few_shot_examples.py`)가 규칙의 기준 사례다.

## 3. 검토했지만 쓰지 않은 방법

| 방법 | 쓰지 않은 이유 |
|---|---|
| ROUGE-1/2/L | 모범 요약문과 단어가 겹치는 정도를 보는 지표인데, 이 데이터에는 모범 요약문이 없다. 출력이 JSON 필드로 나뉘어 문장 비교와 맞지 않고, 한국어는 조사 때문에 형태소 분석 없이는 점수가 크게 흔들린다. |
| 항목별 0~2점 (정책 적합, 핵심 포함, 근거 없는 주장, 명료성) | 기준 자체는 타당하지만 "1점"의 경계가 모호해 채점자마다 판단이 달라지기 쉽다. 같은 네 기준을 아래 체크리스트로 더 잘게 나눠 이어받았다. |
| 칸 규칙 위반을 요약 전체에 대한 예/아니오 하나로 판정 | 판단 범위가 넓어 채점 모델이 오판하고 사람끼리도 갈리기 쉬웠다. 칸마다 맞음/틀림을 판정하는 방식으로 바꿨다. |
| 100점 감점식만 사용 | 숫자 하나로는 어떤 실패인지 보이지 않고, 감점 값에 객관적 기준이 없어 값을 바꾸면 순위가 바뀔 수 있다. 그래서 **모델 선택에는 쓰지 않는 발표용 요약 점수**로만 계산한다. |

## 4. 체크리스트

응답 하나마다 아래를 채운다. 사람 시트의 칸과 LLM 채점 출력이 대응한다.

| 항목 | 입력 | 판정 기준 |
|---|---|---|
| 핵심 내용 (`rp1`~) | 포함 / 부분 / 누락 | `required_points`의 각 번호가 요약 어딘가(어느 칸이든)에 있는지. 일부만 담았으면 부분 |
| 금지 주장 (`fc1`~) | 위반 1 / 0 | `forbidden_claims`의 각 번호를 요약이 주장하면 1 |
| 근거 없는 주장 | 해당 문장 인용, 없으면 빈칸 | 금지 주장 외에 원문에 근거가 없는 내용. 원문의 지칭("대상자" 등)이 가리키는 사람을 문맥상 분명한 범위에서 풀어 쓴 것은 해당하지 않음 |
| 수치·날짜 오류 | 1 / 0 | 수치, 날짜, 시간, 장소, 담당자가 원문과 다름 |
| 외국어 섞임 | 1 / 0 | 외국어 문장이나 불필요한 외국어 단어가 섞임. 원문에 있는 고유명사·약어는 제외 |
| **칸 판정** (`wrong_fields`) | 틀린 칸 이름, 모두 맞으면 빈칸 | `summary`를 뺀 칸마다 아래 칸 규칙대로 채웠는지. LLM은 칸마다 맞음/틀림과 이유 한 줄을 낸다 |
| 어색한 문장 | 1 / 0 | 문법이 틀리거나 뜻이 잘 통하지 않는 문장 |

**칸이 틀린 경우**: 규칙상 다른 칸에 들어갈 내용이 있음, 원문에 있는 정보를 null·[]·"미기재"로 둠, 원문에 없는데 채움, 아직 정하지 않은 것을 결정으로 씀.
**틀림이 아닌 경우**: 회의록에서 결정과 담당이 겹침, 맞는 칸이 없는 정보를 `summary`에 씀.

| 문서 유형 | 칸 판정 대상 |
|---|---|
| 공지 | `audience`, `schedule`, `actions`, `changes` |
| 매뉴얼 | `prerequisites`, `steps`, `cautions` |
| 회의록 | `discussion`, `decisions`, `owners`, `follow_ups` |

**판정 예시** (개발 데이터 `announcement-02`)
- 원문: "청각 지원 강의실의 자막 송출 장치를 금요일 오전에 점검한다. 해당 시간에도 강의실 예약은 유지된다. 자막이 필요한 예약자는 지원 창구에 대체 제공 방식을 문의하기 바란다."
- 응답의 `changes`: "금요일 오전에 청각 지원 강의실의 자막 송출 장치를 점검한다."
- 판정: 점검은 공지를 낸 쪽이 하는 일이고, 물건·장소·규칙·일정이 달라진 것이 아니다 → `changes` **틀림**(null이 맞다). 나머지 세 칸이 맞으면 칸 정확도 0.75, 사용 불가.

### 칸 규칙

null, [], "미기재"는 모두 "원문에 해당 정보 없음"으로 본다. 어느 칸에도 맞지 않는 정보는 `summary`에 쓴다.

| 칸 | 규칙 |
|---|---|
| 공지 `audience` | 원문에 대상이 직접 쓰였거나 원문의 지칭이 가리키는 사람이 문맥상 분명하면 구체적으로. 알 수 없으면 null |
| 공지 `schedule` | 일정 언급이 있으면 미정이어도 그대로. 언급이 없으면 null |
| 공지 `actions` | 대상자가 할 일·하지 말 일만. 공지를 낸 쪽이 하는 일은 제외 |
| 공지 `changes` | 물건·장소·규칙·일정이 실제로 달라진 것(이동, 변경, 중단, 교체, 정정). 새 행사·모집·배포는 아님 |
| 매뉴얼 `prerequisites` | 원문에 "먼저", "~하기 전에", "사전에", "미리" 표시가 있는 행동·준비물만. steps에서 반복하지 않음 |
| 매뉴얼 `steps` / `cautions` | 조건이 붙은 행동도 절차. 주의 사항은 금지·경고만 |
| 회의록 `decisions` | "~하기로 했다", 동의, 보류, 채택하지 않음을 모두. 담당자가 있는 일도 포함. 단, 결정을 미룬 문장("~한 뒤 정하기로 했다")은 제외 |
| 회의록 `owners` | 담당자가 정해진 일을 "담당자: 할 일 (마감)" 형식으로. decisions와 겹쳐도 됨 |
| 회의록 `follow_ups` | 아직 정하지 않고 남긴 것만. "하기로 했다"로 끝나도 결정을 미룬 것이면 여기 |

## 5. 지표

### 5.1 체크리스트에서 계산하는 지표

| 지표 | 정의 | 역할 |
|---|---|---|
| **사용 가능률** | 아래 조건을 모두 만족하는 응답의 비율 | **주 지표.** 자동화에 그대로 써도 되는 요약이 몇 %인가. 모델 선택에 쓴다 |
| 읽기용 사용 가능률 | 사용 가능 조건에서 "칸 오류 없음"만 뺀 비율 | 보조 지표. 사람이 요약을 읽기만 한다면 몇 %가 쓸 만한가 |
| 핵심 포함률 | 핵심 내용별 포함 1, 부분 0.5, 누락 0의 평균 | 필요한 내용을 담았나 |
| 환각률 | 금지 주장 위반 또는 근거 없는 주장이 하나라도 있는 응답의 비율 | 가장 위험한 실패 |
| 칸 오류율 / 칸 정확도 | 틀린 칸이 하나라도 있는 응답의 비율 / 판정한 칸 중 맞은 칸의 비율 | 칸 구분 능력. 어느 칸이 자주 틀리는지도 함께 집계 |
| 수치 오류율, 외국어 섞임률, 어색한 문장 비율 | 해당 항목이 1인 응답의 비율 | 실패 유형 분석 |
| 100점 감점 점수 | 아래 감점표로 계산 | 발표용 요약 숫자. 모델 선택에는 쓰지 않음 |

**사용 가능 조건**: 형식 정상 그리고 환각 없음 그리고 수치·날짜 오류 없음 그리고 외국어 섞임 없음 그리고 핵심 포함률 ≥ 0.67(대략 3개 중 2개 이상) 그리고 **칸 오류 없음**

어색한 문장은 감점에만 반영한다. 읽기 불편하지만 잘못된 정보나 잘못된 자동 처리를 만들지는 않기 때문이다.

### 5.2 100점 감점표

| 항목 | 감점 |
|---|---|
| 환각 (금지 주장 위반 또는 근거 없는 주장) | −20 |
| 수치·날짜·시간·장소·담당자 오류 | −20 |
| 칸 오류 (틀린 칸이 하나라도 있음) | −20 |
| 핵심 내용 누락 | 누락 1개당 −8, 부분 1개당 −4, 합계 최대 −20 |
| 외국어 섞임 | −10 |
| 어색한 문장 | −10 |
| **최대 감점 합계** | **−100** |

- 치명적 오류 4가지(환각, 수치 오류, 칸 오류, 핵심 누락)는 서로 순위를 매기기 어려워 같은 무게(각 20)로 두었다. 읽기 불편 2가지는 각 10이다.
- 모든 항목이 최대로 감점될 때 정확히 0점이 된다.
- 각 항목은 있음/없음으로 한 번만 감점한다(같은 실수가 여러 번 나와도 한 번).
- 예: 핵심 내용 3개 중 부분 1개, `changes` 칸 틀림 → 100 − 4 − 20 = 76점

### 5.3 자동 처리

| 상황 | 처리 |
|---|---|
| 응답이 JSON 형식에 맞지 않음(` ```json ` 코드 블록 표시를 걷어 내도 깨짐) | 채점하지 않고 0점, 사용 불가. 형식 실패율로 따로 보고 |
| 코드 블록으로 감쌌지만 안의 JSON은 정상 | 품질 채점은 진행. 형식(엄격) 위반으로 따로 집계 |
| 외국어 섞임 | 원문에 없는 한자·가나·영문 단어가 요약 값에 있으면 자동으로 "있음"(null 값은 제외). 채점자 판정과 둘 중 하나라도 있음이면 있음 |
| 호출 실패(오류, 시간 초과) | 품질 채점 대상이 아니며 오류율로 따로 보고 |

## 6. 채점 절차

### 6.1 생성 비교 단계와 채점 범위

| 단계 | 입력 | 모델 | LLM 채점 | 사람 채점 |
|---|---|---|---|---|
| 개발 비교 | development 15건 × 1회 | 로컬 5개 (+ 기준선으로 gpt-6-luna) | 전체 | 하지 않음 |
| 최종 비교 | eval 24건 × 2회 | 개발 비교 상위 로컬 2개 + gpt-6-luna | 전체(144건) | 36건 |

- 개발 비교 결과로는 프롬프트와 칸 규칙을 고칠 수 있다. 프롬프트 v2 → v5 → v6의 근거는 [생성 모델 실험 기록](experiment_log_generation.md)에 있다.
- 최종 비교 결과를 본 뒤에는 프롬프트와 이 문서를 바꾸지 않는다.
- 상위 로컬 2개는 개발 비교에서 차례로 고른다. 남은 후보 중 사용 가능률 최고점에서 **0.10 이내는 동점**으로 보고(15건에서 1~2건 차이는 실행마다 바뀔 수 있음), 그 안에서 **환각률이 낮은 순** → 사용 가능률 → 응답 시간 순으로 고른다. 환각은 발견하기도 바로잡기도 어려운 가장 위험한 실패라 동점일 때 우선한다.

### 6.2 LLM 채점

| 항목 | 값 |
|---|---|
| 채점 모델 | `lesson_settings.JUDGE_TARGET` = openai (gpt-6-luna) |
| temperature | 0 |
| 입력 | 원문, 예측 문서 유형과 정책, 칸 규칙, 핵심 내용, 금지 주장, 요약(JSON) |
| 재시도 | 출력 형식이 틀리면 1회 다시 시도. 두 번 다 실패하면 채점 오류로 기록하고 집계에서 뺀다 |
| 금지 주장 판정이 빠진 경우 | 위반 없음으로 채운다(위반한 것만 나열하는 경우가 있어서) |
| 핵심 내용·칸 판정이 빠진 경우 | 채점 오류로 처리한다 |
| 채점 기준이 바뀐 경우 | 같은 버전으로 채점한 응답만 건너뛰고 나머지는 다시 채점한다. 비교는 같은 버전끼리만 한다 |

### 6.3 사람 채점

| 항목 | 방법 |
|---|---|
| 대상 | 최종 비교의 반복 1회분 중 형식이 정상인 응답에서 **36건** |
| 표본 추출 | 모델별 12건 × 문서 유형별 4건을 무작위로(seed 2026). 언제 다시 뽑아도 같은 36건 |
| 채점자 | 팀원 4명이 **같은 36건**을 각자 채점(1인당 약 30~40분) |
| 블라인드 | 모델 이름을 가리고 채점자마다 순서를 다르게 섞는다. 모델 대조표(`human_key.json`)는 채점이 끝날 때까지 열지 않는다 |
| 칸 판정 | 시트의 `checked_fields`에 판정 대상 칸이 적혀 있다. 틀린 칸만 `wrong_fields`에 쉼표로 적고 이유를 `wrong_field_reasons`에 쓴다 |
| 기준 맞추기 | 시작 전에 퓨샷 예시 6건과 development 데이터 3~5건으로 함께 채점하며 판단 기준을 맞춘다. eval 데이터로 연습하지 않는다 |
| 최종 판정 | 체크 항목별·칸별 **다수결**. 2:2 동률은 보수적으로(문제 있음, 부분 포함, 칸 틀림) 정하고 `ties` 목록에 남겨 함께 논의한다 |

### 6.4 일치도

| 지표 | 대상 | 해석 |
|---|---|---|
| Fleiss' kappa | 사람 4명 사이, 예/아니오 항목별(칸 오류 포함) | 사람끼리 얼마나 같은 판단을 하는지. LLM 일치도를 해석하는 기준선 |
| 일치율, Cohen's kappa, PABAK | LLM 판정 vs 사람 다수결, 항목별과 사용 가능 여부 | LLM 채점을 얼마나 믿을 수 있는지. 칸 오류 항목은 따로 보고한다 |
| 피어슨 상관계수 | LLM 감점 점수 vs 사람 감점 점수 | 점수 순위가 비슷한지 |

- kappa는 우연히 일치할 확률을 뺀 값이다. 흔히 0.41~0.60을 보통, 0.61~0.80을 상당한 일치로 본다.
- **kappa의 약점**: 판정이 한쪽으로 몰리면(예: 36건 중 32건이 사용 가능) 실제 일치율이 높아도 kappa가 낮게 나온다. 우연히 일치할 확률이 커져서 그만큼 빼기 때문이다.
- **PABAK** = 2 × 관측 일치율 − 1. 판정 비율이 치우쳐도 덜 흔들린다. 예를 들어 36건 중 34건이 일치하면 PABAK은 0.89다.
- 36건으로 계산한 일치도는 표본이 작아 대략 ±0.2 흔들릴 수 있다. 기준값 근처의 결과는 이 점을 함께 적는다.

## 7. 사람 평가의 역할

사람 평가는 **LLM 채점을 믿을 수 있는지 검증하는 기준**이다. 최종 모델 선택은 아래 순서로 판단한다.

1. 사람 다수결과 LLM의 **사용 가능 여부**(칸 오류 포함) 판정으로 일치도를 구한다.
   - 기본 기준은 **Cohen's kappa**다.
   - 사람과 LLM 판정을 합쳐 "사용 가능"이나 "사용 불가" 한쪽이 **85%를 넘으면** kappa 대신 **PABAK**을 기준으로 쓴다.
2. 기준 값이 **0.7 이상**이면 LLM 채점 결과(144건 전체)로 모델을 비교한다. 사람 36건 결과는 함께 보고한다.
3. 0.7 미만이면 LLM 채점은 참고로만 두고, **사람 다수결 결과(36건)를 우선**해 모델을 비교한다. 표본이 작다는 한계를 함께 적는다.
4. 어느 경우든 kappa, PABAK, 관측 일치율을 모두 보고한다. 칸 오류 항목의 일치도가 특히 낮으면 칸 판정을 믿기 어렵다는 점을 함께 적는다. 사람과 LLM이 엇갈린 항목은 사례로 정리해 LLM 채점의 경향(예: 특정 모델에 후함)을 분석한다.

이 판정은 `aggregate`가 `quality_human.json`의 `agreement.llm_trust_decision`에 기록한다(기준 상수: `common/quality.py`의 `AGREEMENT_THRESHOLD`, `SKEW_RATIO`).

## 8. 생성 모델 최종 선택 규칙

팀 방향(비용 최적화와 온프레미스)에 따라 **품질이 크게 떨어지지 않으면 로컬 모델을 우선**한다. 최종 비교 결과를 보기 전에 정했다.

1. 품질 지표는 7장의 판정에 따라 LLM 채점(144건) 또는 사람 다수결(36건)을 쓴다.
2. 로컬 모델마다 상용 모델(gpt-6-luna)과 비교해 두 조건을 모두 만족하면 **품질 하한 통과**다.
   - 사용 가능률(칸 오류 포함)이 상용 모델보다 **0.10 이하**로만 낮다.
   - 환각률이 상용 모델보다 **0.10 이하**로만 높다.
3. 통과한 로컬 모델이 있으면 그중 사용 가능률 → 환각률(낮은 쪽) → 평균 응답 시간(짧은 쪽) 순으로 하나를 고른다.
4. 통과한 로컬 모델이 없으면 상용 모델을 고르고, 로컬이 어느 조건에서 부족했는지 적는다. 읽기용 사용 가능률도 함께 보고해, 읽기 전용 용도라면 로컬로 충분한지 판단할 근거를 남긴다.
5. 비용, 응답 시간, 메모리, 라이선스 같은 운영 조건은 선택 이유와 함께 보고한다.

코드: `common/quality.py`의 `choose_generation_model`, 기준 상수 `LOCAL_MAX_USABLE_GAP`, `LOCAL_MAX_HALLUCINATION_GAP`. `step09b_score.py select`가 판정해 `generation_selected.json`에 남긴다.

## 9. 한계

- **채점 모델의 자기 편향**: gpt-6-luna는 비교 후보이면서 채점 모델이다. 자기 계열의 답변을 후하게 볼 수 있어, 사람 블라인드 채점과의 일치도로 이를 점검한다.
- **칸 규칙은 팀이 정한 기준이다**: 정답 출력이 없어 칸 판정은 팀의 규칙과 퓨샷 예시에 기댄다. 데이터 문서가 이 칸 구조를 염두에 두고 쓰이지 않아, 어느 칸에도 맞지 않거나 규칙의 경계에 걸리는 문장이 있다.
- **사람 채점 표본**: 36건은 모델당 12건이라 모델 사이의 작은 차이는 구분하기 어렵다.
- **체크 단위**: 근거 없는 주장과 각 오류는 있음/없음으로만 보고 개수는 세지 않는다.
- **채점 기준의 범위**: `required_points`와 `forbidden_claims`가 다루지 않는 오류는 "근거 없는 주장"과 기타 항목에 의존한다.
- **기준값**: 핵심 포함률 0.67, 품질 하한 0.10, 감점 값은 팀이 정한 값이고 실제 사용자 만족도로 검증한 값은 아니다.
