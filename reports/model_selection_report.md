## 1. 문제 정의

- **대상**: 사내 공지, 매뉴얼, 회의록을 읽고 핵심을 빠르게 파악해야 하는 구성원
- **입력**: 문서 원문 한 건
- **출력**: 문서 유형(분류 결과)과 유형에 맞는 요약
- **처리 흐름**: 학습한 분류기가 유형을 예측 → 예측 유형에 맞는 요약 정책 선택 → 생성 LLM이 원문과 정책으로 요약
- **팀 방향: 비용 최적화와 온프레미스**
  - 사내 문서는 외부로 보내기 어려운 내용이 많다.
  - 문서가 길수록 상용 API의 토큰 비용이 커진다.
  - 그래서 로컬 LLM(Ollama)과 상용 API를 품질, 시간, 비용, 운영 조건으로 실측 비교해 근거를 만든다.

### 3.6 선정 규칙과 결과

선정 규칙:
1. seed만 다른 실행을 한 설정으로 묶어 validation Macro-F1 평균을 구한다.
2. 평균 최고점에서 0.01(validation 약 1건) 이내는 동점으로 본다.
3. 동점 후보는 모두 seed 3개 이상이어야 한다.
4. CPU 추론 시간이 가장 빠른 후보의 1.2배 이내는 같은 속도로 본다.
5. 평균 Macro-F1 → 표준편차 → 파라미터 수 순으로 고른다.

**선정 결과: klue/roberta-base (lr 1e-5)**
- 동점 범위의 5개 설정이 모두 같은 속도 구간(18.9~20.9ms)에 들어왔다.
- 그중 평균 1.000이 roberta 1e-5, roberta 5e-5, electra-b 5e-5였고, 세 설정 모두 표준편차가 0이었다.
- 파라미터가 더 적은 roberta가 남았다. 두 학습률은 모든 기준에서 같아, 정해 둔 마지막 기준(설정 이름 순)으로 1e-5를 골랐다.
- 서비스에는 seed 42의 가중치를 쓴다.

| 선정 모델 (validation) | 기준 모델 (validation) |
|---|---|
| ![선정 모델 혼동행렬](figures/classification/confusion_validation_selected.png) | ![기준 모델 혼동행렬](figures/classification/confusion_validation_baseline_reference.png) |

- 기준 모델의 오류 6건은 모두 공지↔매뉴얼 사이에서 났다. 공지 안에 이용 방법("확인한다", "싣지 않는다")이 섞인 문장이 매뉴얼로 분류됐다.
- 회의록은 모든 모델이 한 번도 틀리지 않았다.

### 3.7 분류 단계의 한계

- validation이 120건이고 상위 4개 설정이 1.000으로 포화되어, 상위 모델 사이의 우열은 validation으로 가릴 수 없다.
- 학습률과 epoch는 모든 모델에 같은 조건으로 고정했다. electra-s와 deberta-ko는 더 높은 학습률이나 더 긴 학습에서 결과가 달라질 수 있다.
- CPU 추론 시간은 노트북 한 대에서 측정했고 실행마다 약 ±15% 흔들린다.
- 합성 데이터라 실제 사내 문서보다 짧고 정형적이다.

## 5. 생성 모델 비교 (로컬 vs 상용)

평가 기준: [요약 평가 기준](evaluation_rubric.md) · 상세 기록: [생성 모델 실험 기록](experiment_log_generation.md) · 전체 표: [생성 비교 표](generated/generation_tables.md)

### 5.1 후보와 비교 조건

| 구분 | 모델 | 크기(양자화) | 실행 |
|---|---|---|---|
| 로컬 | qwen3:4b-instruct-2507, gemma3:4b, qwen2.5:7b, exaone3.5:7.8b, llama3.1:8b | 2.5~4.9GB (Q4) | Ollama, RTX 5060 Laptop 8GB |
| 상용 | gpt-6-luna | – | OpenAI Responses API (Standard) |

- 같은 분류 결과와 같은 프롬프트를 모든 모델에 준다. 문서 유형별 JSON 형식으로 요약한다(공지: 대상·일정·할 일·변경 / 매뉴얼: 전제·절차·주의 / 회의록: 논의·결정·담당·후속).
- temperature 0.2, 최대 출력 512토큰. 로컬 모델은 준비 호출로 메모리에 올린 뒤 측정한다(적재 시간은 콜드 스타트로 따로 보고).
- 품질 주 지표는 **사용 가능률**이다. 형식 정상, 환각 없음, 수치 오류 없음, 외국어 없음, 핵심 포함률 0.67 이상인 응답의 비율이다.
- 모델 라이선스와 사용 조건은 제출 전에 공식 페이지에서 확인해 적는다.

### 5.2 1차 비교: 프롬프트와 출력 방식 정하기 (development 15건 × 로컬 5개)

![1차 비교](figures/generation/round1_versions.png)

| 실행 | 바꾼 점 | 결과 |
|---|---|---|
| v2 | 라벨별 JSON 형식 첫 버전 | 정책 위반 40~88%. llama3.1은 형식 실패 47% |
| v3 | 필드 설명 구체화 | 형식 실패 급증(qwen2.5 33%, exaone 40%, llama 80%). 프롬프트의 형식 예시에 쉼표와 타입 표시가 없던 결함이 드러남 |
| v4 | 올바른 JSON 뼈대로 형식 예시 수정 | 모든 모델 형식 실패 0%. llama3.1 사용 가능률 0.07 → 0.67 |
| v4 + 구조화 출력 | 스키마로 출력 토큰 제한 | 모든 모델이 엄격 형식 100%. 품질·속도는 v4와 변동 범위 안에서 비슷 |

**결정**: 프롬프트 v4 + 구조화 출력 사용. 2차 후보는 v4 두 실행(30건)에서 사실상 동점인 상위 3개(llama 0.60, gemma 0.57, qwen2.5 0.57) 중 llama3.1-8b와, 환각률이 더 낮은 qwen2.5-7b(0.13 vs gemma 0.37)로 정했다.

- **분류 오류의 영향**: eval 24건 중 매뉴얼 2건이 공지로 분류되어 공지 형식으로 요약되었다. 세 생성 모델 모두 같은 입력을 받았으므로 비교의 공정성에는 영향이 없다.

- 사람-LLM 사용 가능 판정 일치: Cohen's kappa 0.48 (기준 0.7 미만 → 사람 다수결 우선). **가상 데이터라 의미 없는 값**이며, 실제 채점을 집계하면 다시 판정한다.

### 5.4 생성 모델 선택 (잠정)

선택 규칙(평가 기준 8장, 결과를 보기 전에 정함): 로컬 모델의 사용 가능률이 상용보다 0.10 이하로만 낮고 환각률이 0.10 이하로만 높으면 로컬을 우선한다.

| 로컬 모델 | 사용 가능률 차이 (상용 − 로컬) | 환각률 차이 (로컬 − 상용) | 품질 하한 |
|---|---|---|---|
| qwen2.5-7b | +0.292 | +0.104 | 미달 |
| llama3.1-8b | +0.292 | +0.312 | 미달 |

**잠정 선택: gpt-6-luna** — 두 로컬 모델 모두 품질 하한에 미달했다. 실제 사람 채점 결과로 다시 판정한다.

- 팀 방향(온프레미스)과 다른 결과다. 외부 전송이 허용되지 않는 문서라면 로컬 모델 중 환각이 적은 **qwen2.5-7b**가 대안이지만, 사용 가능률이 약 0.29 낮다는 대가가 있다.

### 5.5 생성 비교의 한계

- **채점 모델의 자기 편향**: gpt-6-luna는 후보이면서 채점 모델이다. 자기 답변을 후하게 봤을 가능성이 있어 사람 블라인드 채점으로 점검해야 한다(현재 미완료).
- **대상(audience) 추론과 환각 판정의 충돌**: 프롬프트 v3부터 "대상이 문맥상 분명하면 적는다"고 지시했는데, 채점에서는 원문에 직접 없는 대상(예: "온라인 특강 참가자")이 근거 없는 주장으로 잡힌 사례가 모든 모델에서 나왔다. 환각률이 실제 위험보다 높게 나왔을 수 있다. eval 결과를 본 뒤라 기준을 바꾸지 않고 한계로 남긴다.
- **표본 크기**: eval 24건 × 2회이고, 1차 비교에서 같은 조건을 두 번 실행했을 때 사용 가능률이 모델당 최대 0.13 달라졌다.
- **짧은 문서**: 기본 데이터는 문서가 약 100자라, 긴 문서에서 생기는 비용·시간 차이는 반영되지 않았다.
