## 3. 관찰 (개발 비교)

1. **칸 규칙과 퓨샷 예시가 가장 큰 개선을 만들었다.** qwen2.5-7b는 v2 → v5 → v6에서 사용 가능률 0.13 → 0.40 → 0.60, 칸 정확도 0.58 → 0.76 → 0.83으로 꾸준히 올랐다.
2. **구조화 출력은 형식 문제를 없앴다.** v5부터 모든 모델이 응답 그대로 JSON을 냈다(엄격 형식 100%). llama3.1의 v2 점수는 대부분 형식 실패 때문이었다.
3. **칸 구분은 큰 모델도 완벽하지 않다.** 같은 규칙과 예시에서 gpt-6-luna의 칸 오류율은 27%, 소형 모델은 40~67%였다. 소형 모델의 한계가 크지만, 데이터 문서가 이 칸 구조를 염두에 두고 쓰이지 않은 영향도 있다.
4. **매뉴얼의 prerequisites는 혼동을 만든다.** 원문에 "먼저" 같은 표시가 없는데 첫 단계를 전제 조건에 넣는 실수가 gpt-6-luna를 포함한 여러 모델에서 나왔다. 심화 데이터 결과를 보고 칸 유지 여부를 정한다.
5. **비용**: 퓨샷 예시로 입력 토큰이 약 300에서 900으로 늘었다. 로컬 응답 시간은 거의 같았고, gpt-6-luna의 1,000건당 비용은 약 $0.11에서 $0.15로 늘었다.

4. qwen3-4b는 공지의 changes 칸에서 오류가 10건으로, 공지를 낸 쪽이 하는 일(점검 등)을 변화로 적는 실수를 반복했다.

### 4.4 사람 채점 표본과 현재 상태

- **채점 대상**: 최종 비교의 응답 144개(24건 × 2회 × 3모델) 중 **36건**을 사람이 채점한다. 반복 1회차의 형식이 정상인 응답에서 모델 × 문서 유형을 균등하게(3 × 3 × 4건) 무작위로 고른 것이라(seed 2026) 모델당 12건이다.
- **왜 36건과 144건이 다른가**: 사람 채점은 한 건에 몇 분씩 걸리고 같은 문서의 반복 응답을 또 채점하는 것은 낭비라서 표본만 본다. LLM 채점은 호출 비용이 작아 144건(모델당 48건) 전부를 했다. **그래서 "사람 36건"과 "LLM 144건"은 서로 다른 표본**이고, 공정하게 비교하려면 LLM 결과를 같은 36건으로 줄여 봐야 한다(4.5).
- **현재 상태**: 1번 시트는 사용자가 실제로 채점했다(2026-10-16). 2~4번 실제 시트는 비어 있다. 집계(`aggregate`)로 모델별 결과를 이미 봤으므로 2~4번 실제 시트를 블라인드로 채우는 의미는 줄었다.
- **가상 채점(미리보기용)**: 일치도 지표(kappa, PABAK)가 어떻게 움직이는지 보려고 1번 시트를 변형한 가상 2~4번 시트를 `human_dummy/`에 만들었다(4.6). 실제 결과가 아니다.
- **생성 모델 선택**: `select`를 실행했다(2026-10-16). 결과는 qwen2.5-7b, status `final`(사람 채점 반영)이다. 실행 전에는 `provisional`(LLM 채점만 반영, gpt-6-luna)이었다.

해석
1. 사람 판정을 쓰면 qwen2.5-7b가 하한을 통과해 선택이 로컬 모델로 바뀔 수 있다. 신뢰 판정이 실패했으므로 사전에 정한 규칙은 사람 36건을 우선한다.
2. **그러나 선택이 바뀐 원인은 사람이 LLM과 다르게 봐서가 아니라 표본이 줄어서다.** 같은 36건을 LLM이 채점해도 qwen2.5-7b의 차이가 +0.083으로 똑같이 통과한다. 48건 기준의 +0.167이 12건 표본에서는 +0.083으로 나온 것이다.
3. **+0.083은 12건 중 정확히 1건 차이다.** 판정 1건이 바뀌면 +0.167로 미달이 된다. 모델당 12건과 채점자 1명으로는 이 차이를 구분할 수 없다.
4. qwen2.5-7b의 환각률 차이는 두 출처 모두 하한 안이고, qwen3-4b는 사람 채점에서 환각률 차이(+0.250)와 사용 가능률 차이(+0.500)가 모두 크게 미달이다.
5. 정리: 선택 규칙대로 `select`를 실행해 qwen2.5-7b를 선택했다(status `final`). 근거가 약하므로 이 한계를 보고서에 크게 적었다.

**`select` 실행 결과** (`generation_selected.json`, 비교 폴더와 `selection/`)

| 항목 | 값 |
|---|---|
| 선택 | qwen2.5-7b (로컬), status `final` |
| 품질 출처 | 사람 채점 36건(LLM 신뢰 판정 kappa 0.349 < 0.7이라 사람 우선) |
| qwen2.5-7b | 사용 가능률 차이 +0.083, 환각률 차이 0.000 → 통과 |
| qwen3-4b | 사용 가능률 차이 +0.500, 환각률 차이 +0.250 → 미달 |
| 사유 | 품질 하한을 만족하는 로컬 모델 중 사용 가능률 → 환각률 → 응답 시간 순 |
| 서비스 영향 | API가 시작할 때 이 파일을 읽어 기본 생성 모델이 qwen2.5-7b가 된다. 자동 라우팅은 일반·기밀 문서 모두 qwen2.5-7b → qwen3-4b(로컬)만 쓴다. 상용은 `target=openai` 직접 지정 때만 |

### 4.6 가상 채점 4명의 일치도 (미리보기용, 실제 결과 아님)

kappa와 PABAK이 실제 일치도 표에서 어떻게 보이는지 확인하려고 만든 가상 데이터다. **보고서에는 "가상 채점(미리보기용)"으로만 쓴다.**

**가상 3명(2~4번)을 만든 방법** (`scripts/make_dummy_from_rater1.py`, seed 11)
1. 1번 시트는 사용자가 실제로 채점한 값 그대로다.
2. 2~4번은 1번 시트의 각 칸을 확률적으로 바꿔 만들었다. 필수 포인트는 한 단계 위아래(포함 ↔ 부분 ↔ 누락), 0/1 칸은 뒤집기, 근거 없는 주장은 추가·삭제, 틀린 칸은 추가·삭제.
3. **기본 변형 확률**: 필수 포인트 5%, 금지 주장 2%, 수치 오류 2%, 외국어 1%, 어색한 문장 10%, 근거 없는 주장 삭제 10%·추가 3%, 틀린 칸 삭제 15%·추가 5%.
4. **애매한 항목은 2.5배**: 1번 채점자가 메모(notes)나 칸 오류 이유(wrong_field_reasons)를 남긴 12행(H24, H04, H23, H03, H10, H20, H27, H34, H31, H13, H01, H30)은 확률을 2.5배로 올렸다. 사람이 애매하다고 느낀 곳에서 다른 채점자도 더 자주 갈린다는 가정이다.
5. **채점자 성향**: 2번은 엄격(칸을 틀렸다고, 내용이 부족하다고 볼 확률이 높음), 3번은 관대, 4번은 중간. 근거 없는 주장과 틀린 칸의 추가·삭제 확률은 성향에 따라 ±50% 조정되고(엄격한 채점자는 "틀림"을 더 자주 추가하고 덜 삭제), 필수 포인트는 바뀔 때 더 엄격한 쪽(덜 포함)으로 갈 확률이 50% ± 25%p로 달라진다.
6. 필수 포인트가 모두 "누락"인 응답(중국어 출력)은 필수 포인트를 바꾸지 않는다.
7. 바뀐 칸은 각 행의 notes에 "가상 채점 (1번과 다르게 판단: …)"으로 남겼다. 결과: 1번과 다른 칸은 2번 26개, 3번 15개, 4번 25개(전체 약 432칸의 3.5~6%).
8. **한계**: 이 확률은 모두 가정이다. 실제 사람 사이의 불일치 정도를 측정한 값이 아니다. 1번을 변형한 것이라 일치도가 실제보다 높게 나온다. 또 LLM 판정은 사용하지 않았다(LLM과의 일치도를 인위적으로 높이지 않으려고).

**가상 4명 일치도**

| 항목 | Fleiss' kappa | 사람 간 PABAK |
|---|---|---|
| hallucination | 0.661 | 0.806 |
| numeric_error | −0.036 | 0.861 |
| foreign_language | 1.000 | 1.000 |
| field_error | 0.604 | 0.648 |
| awkward_sentence | 0.233 | 0.574 |
| usable | 0.554 | 0.556 |

동률로 논의가 필요한 항목은 8개였다. 가상 다수결 vs LLM의 사용 가능 판정은 일치율 0.694, Cohen's kappa 0.349, PABAK 0.389로 1명 결과와 거의 같다(1번이 실제 채점이라 다수결이 1번을 따라가기 때문).

**이 표가 실제라면 어떻게 읽나**

| 항목 | 읽는 법 |
|---|---|
| hallucination: 0.661 / 0.806 | 상당한 일치. 사람들이 환각 여부를 비슷하게 판단하므로 이 판정은 믿을 만하다 |
| numeric_error: **−0.036 / 0.861** | kappa만 보면 "우연보다 못한 일치"지만 PABAK은 높다. **판정이 거의 전부 0**(수치 오류 없음)이라 kappa가 의미를 잃은 경우다. PABAK과 일치율을 본다. 이런 쏠린 항목은 kappa로 해석하지 않는다(아래 4.7) |
| foreign_language: 1.000 / 1.000 | 전부 같다. 다만 외국어가 있는 응답이 1건뿐이라 "일치도가 완벽하다"고 말할 수는 없다 |
| field_error: 0.604 / 0.648 | 경계선의 상당한 일치. 칸 판정은 사람 사이에도 4~5건에 하나꼴로 갈린다. 칸 규칙이 가장 애매한 부분이라는 뜻이다 |
| awkward_sentence: 0.233 / 0.574 | 낮은 일치. 어색한 문장은 주관적이라 사람마다 다르다. 주 지표(사용 가능)에는 쓰이지 않고 감점 점수에만 들어가므로 영향은 작다 |
| **usable: 0.554 / 0.556** | **보통 수준**. 사람 사이에서도 사용 가능 여부가 자주 갈린다는 뜻이다. 모델당 12건의 작은 차이를 구분하기 어려운 이유 중 하나다 |

**사람 간 일치도의 쓰임**: 사람끼리의 일치도는 **LLM 채점을 판단하는 기준선**이다. 사람끼리도 0.554밖에 안 맞는다면, LLM과 사람의 kappa가 0.349라도 "사람 한 명이 다른 사람과 갈리는 정도(0.554)"보다 낮을 뿐 아주 동떨어진 것은 아니다. 반대로 사람 사이가 0.9인데 LLM과 0.349라면 LLM이 문제다. 이 기준선이 없으면 0.349가 나쁜 값인지 판정 자체가 어려운 것인지 알 수 없다. **실제 일치도는 가상이 아니라 서로 다른 사람이 채점해야 구할 수 있다.**

### 4.7 kappa와 PABAK: 무엇이고 어떻게 적용하나

**정의** (판정이 예/아니오 두 값일 때)
- 관측 일치율 po = 같은 판정을 한 비율
- **Cohen's kappa** = (po − pe) / (1 − pe). pe는 두 채점자가 각자의 "예" 비율대로 무작위로 판정해도 우연히 같아질 비율. 우연히 맞은 몫을 빼고 남은 일치를 본다. 채점자가 3명 이상이면 **Fleiss' kappa**를 쓴다.
- **PABAK** = 2 × po − 1. 우연 일치를 판정 비율과 무관하게 50%로 고정한 값. 판정이 한쪽으로 쏠려도 흔들리지 않는다.

**이 프로젝트에서 쓰는 곳**

| 지표 | 비교 대상 | 용도 |
|---|---|---|
| Fleiss' kappa, 사람 간 PABAK | 채점 시트들 사이 (예/아니오 항목별과 사용 가능 여부) | 사람끼리 얼마나 같은 판단을 하는지. LLM 일치도를 해석하는 기준선 |
| Cohen's kappa, PABAK | LLM vs 사람 (여럿이면 다수결) | LLM 채점을 믿을지 정하는 근거 |

**신뢰 판정 규칙** (평가 기준 7장, 결과를 보기 전에 정함): 사용 가능 판정의 일치도가 **0.7 이상**이면 LLM 채점 전체(144건)를 쓰고, 아니면 사람 판정 36건을 쓴다. 사람과 LLM 판정을 합쳐 한쪽이 85%를 넘으면 kappa 대신 PABAK으로 판정한다.

**계산 예 1: 이번 실제 결과 (사용 가능, 사람 vs LLM, 36건)**
- 둘 다 사용 가능 17, 사람만 사용 가능 6, LLM만 사용 가능 5, 둘 다 불가 8 → po = 25/36 = 0.694
- 사람의 사용 가능 비율 23/36, LLM 22/36 → pe = (23/36)(22/36) + (13/36)(14/36) = 0.531
- kappa = (0.694 − 0.531) / (1 − 0.531) = **0.349**, PABAK = 2 × 0.694 − 1 = **0.389**
- 판정이 62.5%만 쏠려 있어 85% 규칙이 적용되지 않고 kappa가 기준이다. 0.349 < 0.7이라 LLM 채점은 쓰지 않는다.

**계산 예 2: 쏠린 항목에서 kappa가 무너지는 경우 (수치 오류)**
- 36건 중 35건은 4명 모두 "오류 없음", 1건에서만 4명 중 1명이 "오류 있음"이라고 하자.
- po = (35 × 1 + 1 × 0.5) / 36 = 0.986 (거의 완벽한 일치)
- "오류 있음"이 144개 판정 중 1개뿐이라 pe = 0.986. kappa = (0.986 − 0.986) / (1 − 0.986) ≈ **−0.007**, PABAK = 2 × 0.986 − 1 = **0.972**
- 일치율이 98.6%인데 kappa는 0 아래다. 한쪽으로 쏠리면 우연 일치가 이미 높아 kappa가 아주 작은 차이에도 크게 흔들린다. 이 때문에 PABAK을 함께 본다(가상 4명의 numeric_error가 이 경우다).

**읽는 법**
- kappa 기준(Landis & Koch): 0.8 이상 거의 완벽 / 0.6~0.8 상당한 일치 / 0.4~0.6 보통 / 0.4 미만 낮음. 이 기준은 관례이며 절대적이지 않다.
- 판정이 한쪽으로 쏠렸을 때(한쪽 85% 초과)는 kappa 대신 PABAK과 일치율을 본다.
- **한 항목만 보지 않는다**: kappa, PABAK, 일치율을 모두 보고, 양성(예) 판정이 아주 적은 항목은 값이 불안정하다고 적는다.
- PABAK은 쏠림에 강한 대신 우연 일치를 50%로 가정해서, 판정이 한쪽으로 쏠린 항목에서는 kappa보다 후하게 나온다. 어느 값이든 단독 근거로 쓰지 않는다.

### 4.8 용어: judge, sheet, aggregate, select

| 명령 | 하는 일 |
|---|---|
| `step09b_score.py judge` | LLM(gpt-6-luna)이 모든 응답을 체크리스트로 채점한다 |
| `sheet` | 사람이 채점할 블라인드 시트(모델 이름 숨김)와 모델 대조표를 만든다 |
| `aggregate` | 사람이 채운 시트를 합쳐 모델별 사람 채점 결과, 채점자 간·사람-LLM 일치도, LLM 신뢰 판정을 `quality_human.json`에 쓴다. 이때 모델 대조표를 연다 |
| **`select`** | **미리 정한 선택 규칙으로 서비스에 쓸 생성 모델을 고른다.** 품질 출처를 정하고(LLM 신뢰 판정이 통과하면 LLM 채점 전체, 아니면 사람 채점), 로컬 모델 중 상용 대비 사용 가능률 차이 ≤ 0.10, 환각률 차이 ≤ 0.10을 만족하는 모델이 있으면 그중 사용 가능률 → 환각률 → 응답 시간 순으로 고르고, 없으면 상용 모델을 고른다. 결과를 `generation_selected.json`(비교 폴더와 `selection/`)에 쓰며 상태(status)는 final(실제 사람 채점 반영) / provisional(LLM 채점만) / dummy(가상)다. **서비스 API는 시작할 때 이 파일을 읽어 기본 생성 모델을 정한다.** |
